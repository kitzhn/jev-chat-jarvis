# Jev Ultimate 使用说明书

> 适用于 `kitzhn/jev-chat-jarvis` 的 Ultimate 版本。  
> 目标：让没有参与开发的朋友也能完成安装、API 接入、联系人关联和日常使用。

## 1. 这是什么

Jev Ultimate 是一个运行在 Android 手机上的聊天副驾。

它通过 Android 无障碍服务读取当前支持的聊天窗口，将聊天内容发送到**用户自己配置的 AI 接口**进行分析，并在悬浮窗中展示判断和候选回复。

它不会自动点击“发送”。最终消息是否发送始终由用户决定。

Ultimate 版在原项目基础上增加：

- 跨 App 联系人身份绑定
- 联系人列表与完整人物画像
- Galgame 风格好感度 0–100
- 信任度 / 亲密度
- 好感变化时间线与变化原因
- 最近互动时间
- 联系人之间的科幻节点关系网络
- GalGame 风格 4 个候选回复策略，一键写入输入框
- 联系人画像参与候选策略加权：亲密/偏好可升权轻松表达，边界可抑制主动推进
- 微信实验自动 OCR：支持无障碍事件触发，也可优先使用微信新消息通知触发；截图限频、本地 ML Kit OCR，默认关闭
- 用户回复习惯学习：按联系人记录实际选择过的四种策略，不修改好感/信任/亲密
- 本地对话场景：闲聊 / 安慰 / 冲突 / 工作 / 约见 / 道歉
- 群聊人物模型：群 Contact + 当前发言人 Person，支持显式绑定当前发言人
- 显式重复联系人合并
- API 快速配置与自定义接口
- 不含密钥的 API 配置 JSON 导入 / 导出
- GitHub Actions 自动构建 APK

## 2. 安装

### 推荐方式：GitHub Actions APK

进入仓库的 **Actions → Build Android Debug APK**，打开最新成功的运行记录，下载：

`jev-ultimate-debug`

解压后安装 APK。

Ultimate Debug 版使用独立 application id：

`io.github.kitzhn.jevultimate.debug`

因此可以和原版 Jev 同时安装，互不覆盖。

Android 最低版本：Android 11（API 30）。

## 3. 首次使用

打开 App 后按首页提示完成三项：

1. **无障碍权限**：允许读取当前聊天窗口结构，以及把候选回复填入输入框。
2. **悬浮窗权限**：允许在聊天软件上方显示 Jev 悬浮球和分析面板。
3. **API Key**：至少需要判断接口的有效密钥。

小米 / HyperOS 用户还建议在系统应用详情中开启：

- 自启动
- 后台运行
- 电池策略：无限制

否则系统可能冻结无障碍服务。

## 4. 最简单的 API 接入方式

进入：

**首页 → API 与设置 → 快速 API 配置**

推荐第一次使用选择：

### OpenRouter 一把 Key

点击：

**推荐：OpenRouter 一把 Key**

它会自动配置：

- 判断接口：OpenRouter + Jev
- 回复接口：OpenRouter
- 视觉接口：OpenRouter

然后只需要在“判断接口”的密钥框填写自己的 OpenRouter API Key。

回复密钥和视觉密钥留空时，会自动回退使用判断接口密钥。

最后分别点击：

- 测试判断
- 测试回复
- 测试视觉

都成功后，点击**保存全部设置**。

### 为什么判断接口和回复接口是分开的

判断接口负责：

- 对方真实意图
- 当前关系张力
- 是否适合立即回复
- 候选回复排序

回复接口负责真正生成候选文字。

因此可以采用例如：

- 判断：Jev / OpenRouter
- 回复：DeepSeek 官方
- 视觉：通义或 OpenRouter

这三路可以完全独立。

## 5. 切换到 DeepSeek 回复

在“快速 API 配置”点击：

**回复切换为 DeepSeek 官方**

然后：

1. 在回复接口填写 DeepSeek API Key。
2. Base URL 应为 `https://api.deepseek.com/v1`。
3. 模型默认 `deepseek-chat`。
4. 点击“测试回复”。

判断接口仍保持原来的 Jev 配置。

## 6. 自定义 API

### 回复 / 视觉接口

支持 OpenAI-compatible Chat Completions API。

Base URL 应填写到 `/v1` 为止，例如：

`https://example.com/v1`

程序会自动请求：

`/chat/completions`

模型名填写服务商实际提供的 model id。

### 判断接口

判断接口不是普通 Chat Completions，它需要 Jev / TypeSafe 对应协议。

内置支持：

- OpenRouter
- 博查 Jev
- TypeSafe
- Vercel AI Gateway
- OpenCode Zen
- 自定义完整 Endpoint

“自定义”判断接口必须填写**完整 POST URL**。

## 7. 把 API 配置发给朋友

在“快速 API 配置”点击：

**复制 API 配置模板（不含密钥）**

得到的 JSON 只包含：

- provider
- base URL
- model

**不会包含任何 API Key。**

朋友在自己的手机上点击：

**从 JSON 导入 API 配置**

粘贴后导入，再自行填写自己的 Key。

示例：

```json
{
  "format": "jev-ultimate-api-config-v1",
  "judgeProvider": "openrouter",
  "judgeBaseUrl": "https://openrouter.ai/api",
  "judgeModel": "typesafe/jev-1.13",
  "replyBaseUrl": "https://openrouter.ai/api/v1",
  "replyModel": "deepseek/deepseek-chat-v3.1",
  "visionBaseUrl": "https://openrouter.ai/api/v1",
  "visionModel": "qwen/qwen2.5-vl-72b-instruct"
}
```

## 8. 联系人系统：一个现实的人，多个平台身份

Ultimate 版不再把“QQ 昵称”“飞书姓名”“X handle”当成三个独立的人。

数据结构是：

```
现实联系人 Contact
├── QQ + 会话标题
├── 飞书 + 会话标题
├── X + 会话标题
├── 其它平台身份
├── 人物画像
├── 好感 / 信任 / 亲密
├── 聊天历史
└── 好感变化历史
```

匹配优先级：

1. **App + 会话标题** 精确身份
2. 旧版本 name / aliases 兼容匹配

不会仅因为两个 App 中出现相同昵称就自动判断为同一个人。

## 9. 创建联系人

有两种方式。

### 方法 A：联系人页面手动创建

首页 → **联系人 · 画像 · 关系网** → 联系人 → 新建联系人。

可以填写：

- 显示名称
- 平台身份
- 关系类型
- 关系阶段
- 好感度
- 信任度
- 亲密度
- 画像标签
- 性格 / 特征
- 沟通偏好
- 边界 / 忌讳
- 备注

### 方法 B：聊天窗口直接保存

打开 QQ / 飞书 / X 中的聊天。

长按 Jev 悬浮球 → **把当前会话存为联系人**。

当前 App 和会话标题会记录成平台身份。

## 10. 把多个软件中的同一个人关联起来

例如：

- QQ：小王
- 飞书：王某某
- X：@wang123

第一次先建立一个联系人，例如“王某”。

然后分别打开对应聊天：

1. 长按 Jev 悬浮球。
2. 点击**关联当前会话到已有联系人**。
3. 联系人列表会显示当前 App 和会话标题。
4. 点击“王某”卡片上的**关联当前会话到这个联系人**。

完成后：

```
QQ: 小王 ───┐
飞书: 王某某 ├── Contact: 王某
X: @wang123 ─┘
```

三处聊天共用同一份画像、关系模型和历史上下文。

## 11. 重复联系人自动合并

如果之前误建成：

- 联系人 A：小王 / QQ
- 联系人 B：王某某 / 飞书

当你从飞书聊天明确选择“关联到联系人 A”时，系统会把 B 合并进 A。

会合并：

- 平台身份
- aliases
- App 列表
- 画像标签
- 聊天历史
- 好感变化记录

主联系人已有的好感 / 信任 / 亲密等核心分数优先保留。

## 12. 好感度系统

好感度范围：0–100。

| 分数 | 阶段 |
| --- | --- |
| 0–19 | 冷淡 |
| 20–39 | 疏远 |
| 40–59 | 普通 |
| 60–79 | 亲近 |
| 80–94 | 信赖 |
| 95–100 | 特别亲密 |

注意：

**这是用户自己的关系管理量表，不表示对方真实心理，也不是 AI 对对方感情的测量。**

## 13. 好感变化记录

联系人卡片提供：

- -5
- +5

点击后可以填写变化原因，例如：

- 一次愉快的见面
- 对方帮了我一个忙
- 出现分歧
- 很久没有联系

每次变化会记录：

- 时间
- 增减值
- 原分数
- 新分数
- 原因
- 修改来源

也可以点击“查看好感记录”查看完整时间线。

## 14. 联系人卡片

联系人列表会展示：

- 首字头像
- 关系阶段徽章
- 好感度进度条
- 信任度
- 亲密度
- 已绑定平台身份
- 最近互动时间
- 画像摘要
- 最近好感变化
- 关系网边数

## 15. 联系人之间的关系网

“关系网”记录的是：

**联系人和联系人之间的关系**

而不是“你和这个联系人的好感”。

例如：

```
张三 ↔ 李四
大学同学
强度 80/100
备注：同一个实验室
```

可以记录：

- 同学
- 同事
- 家人
- 朋友
- 前同事
- 通过某人认识
- 同一个项目组
- 其它自定义关系

每条边包含：

- 联系人 A
- 联系人 B
- 关系类型
- 关系强度 0–100
- 备注

关系网页会以深色科幻节点图展示这些数据：连接最多的联系人自动作为中心节点，联系人显示为发光圆形节点，关系显示为霓虹连线。点击节点可进入联系人画像，点击连线可直接编辑关系。

当当前聊天命中某联系人时，与这个联系人直接相关的关系边也可以进入 AI 背景上下文。

关系网同样只代表用户自己维护的资料。

## 16. 聊天历史

“记录聊天历史”默认是关闭的。

在设置中开启：

**记录聊天历史（只存本机，用于关联上下文）**

之后才会把聊天内容保存到 App 私有目录。

可以设置注入最近多少条历史，范围 0–100。

联系人卡片可以单独清除此人的聊天历史。

## 17. 本地数据位置与隐私

联系人、画像、历史和关系网都保存在 Android App 私有目录，逻辑结构为：

```
filesDir/kb/
├── notes.json
├── contacts.json
├── contact_relations.json
├── logs/
│   ├── <contactId>.json
│   └── <contactId>.screen.json
└── relations/
    └── <contactId>.json
```

API Key 使用 Android 私有 SharedPreferences 保存。

仓库、APK 构建流程和 API 配置模板都不包含用户的联系人数据和 API Key。

## 18. AI 会看到哪些联系人信息

当聊天匹配到联系人时，可以向 AI 提供：

- 关系类型
- 关系阶段
- 好感度
- 信任度
- 亲密度
- 平台身份
- 画像标签
- 性格特征
- 沟通偏好
- 边界 / 忌讳
- 联系人关系网
- 用户开启的历史上下文
- 命中的知识库笔记

同时上下文明确声明：

> 这些分数和画像由用户手动维护，仅作回复背景，不代表对方真实心理。

### 联系人画像如何影响四个 GalGame 选项

四条候选固定带有策略身份：温柔承接、轻松自然、稳妥克制、主动推进。

Jev 先根据当前对话给四条候选排序；随后 App 在本地读取用户自己维护的联系人画像，计算一个小幅“关系先验”乘数，再重新归一化。

典型规则：好感/亲密较高且偏好轻松幽默时，“轻松自然”适度升权；信任/亲密较高且习惯直接安排时，“主动推进”可升权；边界里有“不喜欢被催、不要连续追问、需要空间”等内容时，“主动推进”明显降权；关系处于疏远/冷却或偏好克制简洁时，“稳妥克制”升权。

悬浮候选卡会显示“关系加权 +N% / -N%”。

从 v2.3 起，候选排序还会叠加两层本地先验：

1. **你的实际选择习惯**：每个联系人独立统计你过去点击过温柔 / 轻松 / 稳妥 / 主动各多少次。样本少时影响很弱，使用时间越长才逐渐形成你的个人回复风格。该学习不会改变好感、信任或亲密度。
2. **当前对话场景**：本地识别闲聊、安慰、冲突、工作、约见、道歉。例如冲突场景会适度提高稳妥/温柔，约见场景会提高主动推进。场景判断不新增 API 请求。

最终分数逻辑是：

`Jev 当前对话概率 × 联系人关系先验 × 用户选择习惯先验 × 场景先验`

然后重新归一化。联系人卡片会显示“你的回复习惯”百分比分布。

设置中可关闭 **启用自适应候选排序（画像 + 习惯 + 场景）**；关闭后不使用这些本地加权层，完全按 Jev 当前对话排名。还可以单独关闭 **学习我的 GalGame 选项习惯（仅本机计数）**，停止新增学习样本。

## 19. 当前支持的软件

专用 Adapter 当前主要覆盖：

- QQ
- X
- 飞书

其它 App 可以尝试手动 OCR。

### 微信实验自动 OCR

微信不走消息节点 Adapter。可在设置中主动开启 **微信实验模式：新消息后自动 OCR**。

开启后有两种触发方式：

- **无障碍事件模式**：检测微信窗口发生非输入框内容变化；滚动旧聊天记录、正在编辑输入框时不主动截图。变化停止约 0.9 秒后才尝试截图。
- **通知优先模式（v2.3 推荐）**：再开启“微信优先用新消息通知触发 OCR”，并授予通知读取权限。此时普通界面刷新不再安排自动截图，只有收到微信新消息通知且你此刻正在微信前台时，才计划一次 OCR。通知正文不会被保存，通知标题仅作为会话提示。

两次自动截图至少间隔约 4 秒。截图通过 Android Accessibility screenshot API 获取，ML Kit 中文 OCR 在本机识别图片，再按 OCR 文字块靠近左/右边缘的程度保守推断 `other / me`。

只有最新识别到的聊天气泡更像“对方消息”，且自动分析开启时，才会自动生成判断和回复。如果微信、系统或 ROM 拒绝截图（例如 FLAG_SECURE），该轮只会失败/降级，不会绕过限制，也不会自动发送消息。

注意：原始截图由本机 OCR 处理；一旦进入 AI 分析，OCR 得到的文字仍会发送到你自己配置的模型接口。

### 群聊人物模型（v2.3）

群聊不再只能作为一个整体联系人。内部结构可以是：

```
群 Contact
├── 当前发言人 Person A
├── Person B
└── Person C
```

当适配器能够可靠得到发送者昵称时，当前发言人的人物画像优先参与本轮回复策略；群 Contact 仍作为会话背景保留。

目前：
- QQ：尝试使用发送者昵称节点与消息气泡位置匹配。
- X：使用每条消息自带的发送者标签。
- 微信 OCR：如果截图里拿不到可靠昵称，不会猜测人物，只保留群整体上下文。

在已识别群聊中，长按 Jev 悬浮球可选择 **关联当前发言人到已有联系人**，把群里的昵称显式绑定到现实人物。程序不会自动判断两个昵称是不是同一个人。

群聊历史统一保存在群 Contact 下，每条历史仍保留可识别的 speaker。当前发言人 Person 只负责本轮人物画像、关系数据和策略适配，因此不会把其他群成员的群消息污染进某个人的私聊历史。群成员身份按 **App + 群名 + 发言人昵称** 保存；不同群里的同名成员不会自动合并，必须由用户显式关联。

## 20. 悬浮球常用操作

点击悬浮球：

- 展开 / 收起分析面板

长按悬浮球：

- 截屏识别一次
- 把当前会话存为联系人
- 关联当前会话到已有联系人
- 打开设置
- 隐藏助手

候选回复现在以 GalGame 风格的 A / B / C / D 四个选项卡展示。点击整张选项卡会直接把该回复写入聊天输入框并收起悬浮层；长按选项可复制。

**任何情况下都不会自动发送。** 用户仍需检查输入框内容并自己点击发送。

## 21. 给朋友分享时的推荐流程

推荐你只分享：

1. APK
2. 本说明书
3. 不含密钥的 API 配置 JSON

不要分享：

- 你自己的 API Key
- 你的 contacts.json

朋友应该使用自己的 API Key 和自己的联系人数据。

## 22. 常见问题

### 安装时提示与原版冲突

Ultimate Debug 已使用独立包名后缀，最新构建应可与官方版并存。

如果使用自行编译的 Release 包，请确认 applicationId 和签名配置。

### 首页显示“密钥未设”

至少需要判断接口 Key。

最简单方式是套用 OpenRouter 一把 Key，然后填写判断接口 Key。

### 判断成功，回复失败

通常是回复接口：

- Base URL 错误
- 模型名错误
- Key 不属于该服务商

单独点击“测试回复”。

### 飞书读不到文字

飞书部分页面可能需要 OCR。

开启：

**树读不到正文时用 OCR 兜底**

### 微信为什么没有反应

微信实验自动 OCR 默认关闭。到“设置 → 分析”开启 **微信实验模式：新消息后自动 OCR**。

如果开启后仍失败，先把 Jev 的无障碍服务关掉再重新开启一次，以确保系统应用了 `canTakeScreenshot=true`。如果仍提示窗口受保护或截图失败，则当前微信版本 / ROM 可能拒绝 Accessibility screenshot；App 不会绕过该限制。

### 联系人匹配错了

优先检查“平台身份”。

推荐不要只依赖全局 alias，而是建立：

`App + 会话标题`

精确身份。

### 同一个人被建立了两次

在其中一个聊天窗口：

**长按悬浮球 → 关联当前会话到已有联系人**

选择你想保留的主联系人。

系统会显式合并重复联系人。

## 23. 安全建议

- API Key 不要提交 GitHub。
- 不要把包含真实联系人和聊天记录的 App 私有数据上传公开仓库。
- 给朋友只分享无密钥配置。
- 开启聊天历史前明确知道它会把聊天内容写入本机。
- 好感度、画像和关系网是个人记录工具，不应被当作对他人真实心理、意图或情感的客观测量。

## 25. 固定签名与长期更新

如果只是自己试用，Actions 里的 Debug APK 已经可以直接安装。

如果要长期发给朋友并且以后希望“直接覆盖升级、不丢本地数据”，建议使用固定 Release 签名。

仓库已经提供手动工作流：

**Actions → Build Signed Ultimate Release**

稳定版 application id：

`io.github.kitzhn.jevultimate`

需要在 GitHub 仓库 Settings → Secrets and variables → Actions 中添加 4 个 Secrets：

- `JEV_KEYSTORE_B64`：keystore 文件的 Base64 内容
- `JEV_STORE_PASSWORD`
- `JEV_KEY_ALIAS`
- `JEV_KEY_PASSWORD`

这些 Secrets 不会写入仓库。

配置后手动运行 Release workflow，会生成：

`jev-ultimate-release`

请长期保存原始 keystore。以后所有正式版本必须使用同一签名，否则 Android 无法覆盖安装旧版本。

Debug 包和 Release 包使用不同 application id，因此可以同时安装；Debug 用于测试，Release 用于长期分发。

## 26. 数据模型概览

```
Chat App
   │
   ▼
PlatformIdentity
   │
   ▼
Contact
├── Profile
├── Affection / Trust / Closeness
├── RelationshipEvent[]
├── Chat History[]
└── ContactRelation[]
       │
       ├── Contact B
       ├── Contact C
       └── Contact D
```

最终目标是让 AI 面对不同软件、不同昵称和不同历史时，仍然能够识别“这是同一个现实联系人”，并使用用户自己维护的背景信息提供更一致的回复辅助。
