# Jev Ultimate 使用说明书

> 适用于 `kitzhn/jev-chat-jarvis` 的 Ultimate 版本。  
> 目标：让没有参与开发的朋友也能完成安装、API 接入、联系人关联和日常使用。

## 1. 这是什么

Jev Ultimate 是一个运行在 Android 手机上的聊天副驾。

它通过 Android 无障碍服务读取当前支持的聊天窗口，将聊天内容发送到**用户自己配置的 AI 接口**进行分析，并在悬浮窗中展示判断和候选回复。

它不会自动点击“发送”。最终消息是否发送始终由用户决定。

Ultimate 版在原项目基础上增加：

- 跨 App 联系人身份绑定
- 联系人列表与完整人物画像
- Galgame 风格好感度 0–100
- 信任度 / 亲密度
- 好感变化时间线与变化原因
- 最近互动时间
- 联系人之间的科幻节点关系网络
- GalGame 风格 4 个候选回复策略，一键写入输入框
- 联系人画像参与候选策略加权：亲密/偏好可升权轻松表达，边界可抑制主动推进
- 微信实验自动 OCR：支持无障碍事件触发，也可优先使用微信新消息通知触发；截图限频、本地 ML Kit OCR，默认关闭
- 用户回复习惯学习：按联系人记录实际选择过的四种策略，不修改好感/信任/亲密
- 本地对话场景：闲聊 / 安慰 / 冲突 / 工作 / 约见 / 道歉
- 群聊人物模型：群 Contact + 当前发言人 Person，支持显式绑定当前发言人
- 显式重复联系人合并
- API 快速配置与自定义接口
- 不含密钥的 API 配置 JSON 导入 / 导出
- GitHub Actions 自动构建 APK

## 2. 安装

### 推荐：固定签名正式版

长期自己使用或发给朋友，优先安装 GitHub Release 中的固定签名正式版：

- **[Jev Ultimate 2.5.2 ARM64 APK](https://github.com/kitzhn/jev-chat-jarvis/releases/latest/download/jev-ultimate-arm64.apk)**
- [SHA-256 校验文件](https://github.com/kitzhn/jev-chat-jarvis/releases/latest/download/jev-ultimate-arm64.apk.sha256)
- [v2.5.2 发布页](https://github.com/kitzhn/jev-chat-jarvis/releases/tag/v2.5.2)
- [全部 Releases](https://github.com/kitzhn/jev-chat-jarvis/releases)

正式版 application id：`io.github.kitzhn.jevultimate`。固定签名的好处是后续可以直接覆盖升级，App 私有数据、联系人与设置会继续保留。

### Debug 测试版

[Build Android Debug APK](https://github.com/kitzhn/jev-chat-jarvis/actions/workflows/build-debug.yml) 的最新成功运行会产出 `jev-ultimate-debug`。Debug application id 为 `io.github.kitzhn.jevultimate.debug`，可以和正式版并存。

普通可下载 Debug APK 的 CI 测试组件默认**不导出**；只有 Android 模拟器回归设置 `JEV_INTEGRATION_FIXTURES=1` 时才临时开放测试入口。但 Debug 仍主要用于开发 / 测试，不建议作为朋友长期使用的分发包。

Android 最低版本：Android 11（API 30）。当前正式包面向 ARM64 / `arm64-v8a`。

## 3. 首次使用

建议严格按下面顺序配置：

1. **无障碍权限**：用于读取已允许会话的当前窗口结构、执行 Accessibility screenshot，以及把候选回复填入输入框。
2. **悬浮窗权限**：用于显示悬浮球和分析面板。
3. **API 配置**：至少配置有效的判断接口；回复 / 视觉是否可继承 Key 取决于是否与上游路由属于同一 API origin。
4. **会话白名单**：每行填写一个允许分析的完整会话标题。白名单为空时默认不读取正文。
5. **打开 Jev 总开关**。

小米 / HyperOS 等国产 ROM 建议再开启：

- 自启动
- 后台运行
- 电池策略：无限制

关闭 Jev 总开关后，前台 KeepAlive 会停止；不会继续为了保活而保持 `START_STICKY` 常驻。

如果从很早的版本升级后 OCR / 截屏一直不可用，可把系统里的 Jev 无障碍服务关掉一次再重新开启，让新的截屏能力重新绑定。

### 微信额外权限

微信实验自动 OCR 默认关闭。若启用“通知优先触发 OCR”，还需要授予**通知读取权限**。通知正文不会被保存；通知标题只用于和当前打开会话做匹配。

## 4. 最简单的 API 接入方式

进入：**首页 → API 与设置 → 快速 API 配置**。

第一次使用最简单的是 **OpenRouter 一把 Key**：

1. 点击“推荐：OpenRouter 一把 Key”。
2. 判断 / 回复 / 视觉三路会同时指向 OpenRouter。
3. 只在判断接口填写自己的 OpenRouter API Key。
4. 回复 Key、视觉 Key 可以留空，因为这三路属于同一 API origin。
5. 分别点击“测试判断 / 测试回复 / 测试视觉”。
6. 全部符合预期后点击“保存全部设置”。

### 2.5.2 的密钥继承规则

Key 不再因为“看起来像同一家服务商”就随意复用，而是要求 URL 的 **scheme + hostname + 有效端口**一致。

例如：

- 判断 `https://openrouter.ai/...`，回复 `https://openrouter.ai/...` → 可以继承。
- 判断 OpenRouter，回复 `https://api.deepseek.com/v1` → **不能继承**，回复必须填写 DeepSeek Key。
- 自定义镜像域名即使代理 OpenRouter，也不会被当成官方 `openrouter.ai`。

这个限制的目的是避免把 A 服务商的 Bearer Key 意外发到 B 服务商。

### 为什么判断接口和回复接口分开

判断接口负责意图 / 风险 / 回复时机 / 候选排序；回复接口负责生成实际文字。视觉接口主要用于视觉连通测试和兼容视觉模型能力，因此三路可以完全独立配置。

## 5. 切换到 DeepSeek 回复

在“快速 API 配置”点击：

**回复切换为 DeepSeek 官方**

然后：

1. 在回复接口填写 DeepSeek API Key。
2. Base URL 应为 `https://api.deepseek.com/v1`。
3. 模型默认 `deepseek-flash`。
4. **“DeepSeek 官方：启用 thinking（高级）”默认关闭。** Jev 的短回复与视觉/OCR通常不需要额外推理，因此默认显式发送 `thinking.type=disabled`。
5. 如果确实需要推理，可打开该高级开关；此时回复和视觉/OCR共用这个设置，并且程序不会发送 `temperature`，因为 DeepSeek thinking 模式下该参数不生效。
6. 点击“测试回复”。

判断接口仍保持原来的 Jev 配置。

## 6. 自定义 API

### 回复 / 视觉接口

支持 OpenAI-compatible Chat Completions API。

Base URL 应填写到 `/v1` 为止，例如：

`https://example.com/v1`

程序会自动请求：

`/chat/completions`

模型名填写服务商实际提供的 model id。

### 判断接口

判断接口不是普通 Chat Completions，它需要 Jev / TypeSafe 对应协议。

内置支持：

- OpenRouter
- 博查 Jev
- TypeSafe
- Vercel AI Gateway
- OpenCode Zen
- 自定义完整 Endpoint

“自定义”判断接口必须填写**完整 POST URL**。

## 7. 把 API 配置发给朋友

在“快速 API 配置”点击：

**复制 API 配置模板（不含密钥）**

得到的 JSON 只包含：

- provider
- base URL
- model

**不会包含任何 API Key。**

朋友在自己的手机上点击：

**从 JSON 导入 API 配置**

粘贴后导入，再自行填写自己的 Key。

示例：

```json
{
  "format": "jev-ultimate-api-config-v1",
  "judgeProvider": "openrouter",
  "judgeBaseUrl": "https://openrouter.ai/api",
  "judgeModel": "typesafe/jev-1.13",
  "replyBaseUrl": "https://openrouter.ai/api/v1",
  "replyModel": "deepseek/deepseek-v4.1-flash",
  "visionBaseUrl": "https://openrouter.ai/api/v1",
  "visionModel": "qwen/qwen2.5-vl-72b-instruct"
}
```

## 8. 联系人系统：一个现实的人，多个平台身份

Ultimate 的核心身份模型是：

```text
现实联系人 Contact
├── QQ + 会话标题
├── 飞书 + 会话标题
├── X + 会话标题
├── 群聊中的 App + 群名 + 发言人昵称
├── 人物画像 / 边界
├── 好感 / 信任 / 亲密
├── 聊天历史
└── 好感变化历史
```

### 当前匹配规则

1. **App + 会话标题** 的精确平台身份优先。
2. 旧数据如果只有 `name / aliases / apps[]`，只允许在 `apps[]` 已明确包含**当前 App**时做同 App 兼容匹配。
3. 不同 App 中出现相同姓名 / alias 时，**不会自动认定为同一个现实人物**。
4. 跨 App、跨群聊人物绑定必须由用户显式选择“关联当前会话 / 当前发言人到已有联系人”。

例如 QQ 里叫“张三”、飞书里也叫“张三”，系统不会仅凭同名把两者合并。只有你确认是同一个人并手动关联后，才共享同一份画像与历史上下文。

这样做是为了避免常见昵称、重名或群成员同名导致人物画像串错。

## 9. 创建联系人

有两种方式。

### 方法 A：联系人页面手动创建

首页 → **联系人 · 画像 · 关系网** → 联系人 → 新建联系人。

可以填写：

- 显示名称
- 平台身份
- 关系类型
- 关系阶段
- 好感度
- 信任度
- 亲密度
- 画像标签
- 性格 / 特征
- 沟通偏好
- 边界 / 忌讳
- 备注

### 方法 B：聊天窗口直接保存

打开 QQ / 飞书 / X 中的聊天。

长按 Jev 悬浮球 → **把当前会话存为联系人**。

当前 App 和会话标题会记录成平台身份。

## 10. 把多个软件中的同一个人关联起来

例如：

- QQ：小王
- 飞书：王某某
- X：@wang123

第一次先建立一个联系人，例如“王某”。

然后分别打开对应聊天：

1. 长按 Jev 悬浮球。
2. 点击**关联当前会话到已有联系人**。
3. 联系人列表会显示当前 App 和会话标题。
4. 点击“王某”卡片上的**关联当前会话到这个联系人**。

完成后：

```
QQ: 小王 ───┐
飞书: 王某某 ├── Contact: 王某
X: @wang123 ─┘
```

三处聊天共用同一份画像、关系模型和历史上下文。

## 11. 显式合并重复联系人

如果之前误建成两个联系人，例如：

- 联系人 A：小王 / QQ
- 联系人 B：王某某 / 飞书

你可以在当前聊天中明确选择“关联到联系人 A”。如果当前身份已经属于 B，系统会执行显式合并。

合并内容包括平台身份、aliases、App 列表、画像标签、聊天历史、关系变化记录、策略选择统计等；主联系人已有的核心关系分数优先保留。

### 2.5.2 的事务保护

合并前会先读取一份完整知识库快照。联系人文件、历史、关系事件、关系图或源联系人文件删除中的任一步失败，操作会报告失败并尝试把整份知识库恢复到合并前状态。

联系人删除也使用相同的整库快照回滚语义，避免出现“联系人删了但关系边还在”或“提示失败但历史已经被改掉”的半提交状态。

如果设备本身已经处于严重存储故障状态，回滚也可能失败，因此重要联系人数据仍建议定期使用本地加密备份。

## 12. 好感度系统

好感度范围：0–100。

| 分数 | 阶段 |
| --- | --- |
| 0–19 | 冷淡 |
| 20–39 | 疏远 |
| 40–59 | 普通 |
| 60–79 | 亲近 |
| 80–94 | 信赖 |
| 95–100 | 特别亲密 |

注意：

**这是用户自己的关系管理量表，不表示对方真实心理，也不是 AI 对对方感情的测量。**

## 13. 好感变化记录

- -5
- +5

- 一次愉快的见面
- 对方帮了我一个忙

每次变化会记录：

- 时间

也可以点击“查看好感记录”查看完整时间线。

## 15. 联系人之间的关系网

“关系网”记录的是：

**联系人和联系人之间的关系**

而不是“你和这个联系人的好感”。

例如：

```
张三 ↔ 李四
大学同学
强度 80/100
备注：同一个实验室
```

可以记录：

- 同学
- 同事
- 家人
- 朋友
- 前同事
- 通过某人认识
- 同一个项目组
- 其它自定义关系

每条边包含：

- 联系人 A
- 联系人 B
- 关系类型
- 关系强度 0–100
- 备注

关系网页会以深色科幻节点图展示这些数据：连接最多的联系人自动作为中心节点，联系人显示为发光圆形节点，关系显示为霓虹连线。点击节点可进入联系人画像，点击连线可直接编辑关系。

当当前聊天命中某联系人时，与这个联系人直接相关的关系边也可以进入 AI 背景上下文。

关系网同样只代表用户自己维护的资料。

## 16. 聊天历史

“记录聊天历史”默认关闭。只有你在设置里主动打开 **记录聊天历史（只存本机，用于关联上下文）** 后，Jev 才会把关联消息保存到 App 私有目录。

可以设置每次分析注入最近多少条历史，范围 0–100。每个联系人的详细历史最多保留 300 条。

历史去重不是“相同文字永久只保留一次”，而是根据**上一屏和当前屏的消息序列重叠**判断新出现的尾部内容；因此同一句话在不同时间 / 不同位置真实重复出现时可以分别保留。

联系人卡片可单独清除此人的聊天历史。2.5.2 起，清除操作会检查底层历史文件和屏幕去重文件是否真实删除成功；失败会明确提示，不再无条件显示成功。

## 17. 本地数据位置与隐私

联系人、画像、历史和关系网保存在 Android App 私有目录，逻辑结构为：

```text
filesDir/kb/
├── notes.json
├── contacts.json
├── contact_relations.json
├── logs/
│   ├── <contactId>.json
│   └── <contactId>.screen.json
└── relations/
    └── <contactId>.json
```

API Key 与普通设置保存在 App 私有 SharedPreferences；API 配置 JSON 导出**不包含 Key**。

### 本地加密备份

设置中的“本地加密备份与删除”可以为知识库创建多份 `.jevbackup`：

- 使用 Android Keystore 中的 AES-GCM 密钥加密。
- 只备份知识库数据，不包含 API Key / 接口凭据。
- 仅当前设备、当前 App 安装可恢复，不用于跨设备迁移。
- 清空当前知识库不会自动删除这些备份。
- 删除最后一份 / 全部备份时会同步清理解密密钥。

### 删除与回滚

2.5.2 起联系人合并和删除使用整份知识库快照回滚。关键文件操作失败会报告失败并尝试恢复；“清空知识库与历史”也会确认目录是否实际删除。

仓库、APK 构建流程、Debug fixture 和无密钥配置模板均不包含用户真实联系人、聊天正文或 API Key。

### 剪贴板

候选回复填入失败时可能暂存到系统剪贴板；长按候选也会主动复制。Android 13+ 会将 Jev 创建的回复剪贴板标记为敏感内容。自动粘贴成功或会话失效时，如果剪贴板仍是 Jev 写入的那一条，会尝试清除，不覆盖用户之后复制的新内容。

## 18. AI 会看到哪些联系人信息

当聊天匹配到联系人时，依据你的开关和本地数据，模型背景可能包含：

- 关系类型 / 关系阶段
- 好感度 / 信任度 / 亲密度
- 平台身份
- 画像标签、性格特征、沟通偏好
- 边界 / 忌讳
- 联系人关系网中与当前联系人直接相关的关系
- 用户开启的历史上下文
- 命中的知识库笔记
- 群聊中可可靠识别的当前发言人画像

上下文会明确声明这些内容是用户手动维护的资料，不代表对方真实心理。

### 背景长度保护

2.5.2 起，最终发送给模型的 `background` 有约 **2400 字符硬上限**。联系人画像、关系网和常驻笔记即使非常长，也不会无限扩张请求；超出部分会截断并加上提示。

这个上限针对 background，不影响当前屏幕对话和你单独配置的历史条数逻辑。

### 联系人画像如何影响四个 GalGame 选项

四条候选固定带有策略身份：温柔承接、轻松自然、稳妥克制、主动推进。

最终排序为：

`Jev 当前对话概率 × 联系人关系先验 × 用户选择习惯先验 × 场景先验`

再重新归一化。

关系先验只做有限加权：例如亲密关系和轻松偏好可以适度提高“轻松自然”；明确写有“不要催 / 需要空间”等边界时会压低“主动推进”。

用户选择习惯按联系人本地计数，样本少时影响弱；它**不会修改好感、信任或亲密度**。场景层在本地识别闲聊 / 安慰 / 冲突 / 工作 / 约见 / 道歉，不新增 API 请求。

设置中可以关闭自适应候选排序，也可以单独关闭“学习我的 GalGame 选项习惯”。

## 19. 当前支持的软件

专用 Adapter 当前主要覆盖：

- QQ
- X
- 飞书

其它 App 可以尝试手动 OCR。

### 微信实验自动 OCR

微信不走消息节点 Adapter。可在设置中主动开启 **微信实验模式：新消息后自动 OCR**。

开启后有两种触发方式：

- **无障碍事件模式**：检测微信窗口发生非输入框内容变化；滚动旧聊天记录、正在编辑输入框时不主动截图。变化停止约 0.9 秒后才尝试截图。
- **通知优先模式（v2.3 推荐）**：再开启“微信优先用新消息通知触发 OCR”，并授予通知读取权限。此时普通界面刷新不再安排自动截图，只有收到微信新消息通知且你此刻正在微信前台时，才计划一次 OCR。通知正文不会被保存，通知标题仅作为会话提示。

两次自动截图至少间隔约 4 秒。截图通过 Android Accessibility screenshot API 获取，ML Kit 中文 OCR 在本机识别图片，再按 OCR 文字块靠近左/右边缘的程度保守推断 `other / me`。

只有最新识别到的聊天气泡更像“对方消息”，且自动分析开启时，才会自动生成判断和回复。如果微信、系统或 ROM 拒绝截图（例如 FLAG_SECURE），该轮只会失败/降级，不会绕过限制，也不会自动发送消息。

注意：原始截图由本机 OCR 处理；一旦进入 AI 分析，OCR 得到的文字仍会发送到你自己配置的模型接口。

### 群聊人物模型（v2.3）

群聊不再只能作为一个整体联系人。内部结构可以是：

```
群 Contact
├── 当前发言人 Person A
├── Person B
└── Person C
```

当适配器能够可靠得到发送者昵称时，当前发言人的人物画像优先参与本轮回复策略；群 Contact 仍作为会话背景保留。

目前：
- QQ：尝试使用发送者昵称节点与消息气泡位置匹配。
- X：使用每条消息自带的发送者标签。
- 微信 OCR：如果截图里拿不到可靠昵称，不会猜测人物，只保留群整体上下文。

在已识别群聊中，长按 Jev 悬浮球可选择 **关联当前发言人到已有联系人**，把群里的昵称显式绑定到现实人物。程序不会自动判断两个昵称是不是同一个人。

群聊历史统一保存在群 Contact 下，每条历史仍保留可识别的 speaker。当前发言人 Person 只负责本轮人物画像、关系数据和策略适配，因此不会把其他群成员的群消息污染进某个人的私聊历史。群成员身份按 **App + 群名 + 发言人昵称** 保存；不同群里的同名成员不会自动合并，必须由用户显式关联。

## 22. 常见问题

### 首页显示“密钥未设”

至少需要一个有效的判断接口 Key。最简单是套用“OpenRouter 一把 Key”方案，然后只填判断 Key。

### 判断成功，回复或视觉失败

先检查 Base URL、模型名和对应路由的 Key。2.5.2 起不同 API origin 不再继承判断 Key：如果判断是 OpenRouter、回复是 DeepSeek，DeepSeek 路由必须填写自己的 Key。

### 为什么自定义 OpenRouter 镜像没有自动带 OpenRouter 专属 Header？

OpenRouter / DeepSeek 的专属行为现在按精确 hostname 判断。只有官方 `openrouter.ai` / `api.deepseek.com` 会启用对应专属逻辑；自定义代理不会因为 URL 字符串里碰巧包含这些字样而被误识别。

### 为什么 HTTP 自定义接口被拒绝？

聊天正文和 API Key 只允许通过 HTTPS 离开设备。HTTP 仅允许 `localhost`、`127.0.0.1`、`::1` 这类本机回环调试地址。

### 飞书读不到文字

开启 **树读不到正文时用 OCR 兜底**，并确认无障碍服务具有截屏能力。飞书正文自绘时会按气泡矩形做本地 ML Kit OCR。

### 微信为什么没有反应

微信实验自动 OCR 默认关闭。开启后若仍无反应：

1. 确认当前会话标题已加入白名单。
2. 如果使用通知优先模式，确认通知读取权限已授予。
3. 关闭并重新打开 Jev 无障碍服务。
4. 如果系统提示受保护窗口 / 截图失败，则该微信版本或 ROM 可能拒绝 Accessibility screenshot；Jev 不会绕过。

### 两个 App 里有同名联系人，会自动串在一起吗？

不会。实时匹配以 **App + 会话标题** 为核心；旧数据也只在同 App 范围做兼容。跨 App 必须由你显式关联。

### 同一个人被建立了两次怎么办？

打开其中一个聊天：**长按悬浮球 → 关联当前会话到已有联系人**，选择要保留的主联系人。系统会显式合并；如果底层写入失败，会报告失败并尝试回滚。

### 清空历史 / 删除联系人提示失败怎么办？

先不要反复操作，检查手机剩余空间，再在“本地加密备份与删除”创建一份备份。2.5.2 已改为检查真实文件结果，因此“失败”表示某一步确实没有完整完成，而不是 UI 假成功。

### 关闭 Jev 后为什么不应该继续有前台保活通知？

2.5.2 起 KeepAlive 与总开关绑定。关闭助手后前台保活服务会停止；如果 ROM 仍显示旧通知，可从系统通知栏清掉或重新打开 App 确认总开关状态。

### 安装时提示与其它版本冲突

正式版、Debug 使用不同 application id，理论上可并存。自行编译的 Release 若修改过 applicationId 或签名，则需要按 Android 的签名规则处理升级 / 卸载。

## 23. 安全建议

- API Key 不要提交 GitHub。
- 不要把包含真实联系人和聊天记录的 App 私有数据上传公开仓库。
- 给朋友只分享无密钥配置。
- 开启聊天历史前明确知道它会把聊天内容写入本机。
- 好感度、画像和关系网是个人记录工具，不应被当作对他人真实心理、意图或情感的客观测量。

## API 消耗仪表盘

首页新增 **API 消耗仪表盘**。

它会在本机统计 Jev Ultimate 发出的三类接口请求：

- 判断接口（Jev）
- 回复接口
- 视觉接口

仪表盘显示：

- 今日请求次数与预计费用
- 本月请求次数与预计费用
- 输入 token
- 输出 token
- 缓存命中 token
- 按接口 / 模型拆分的消耗
- token 是否来自 API 真实 `usage`
- 哪些请求只能估算 token
- 哪些自定义模型暂时没有内置价格

统计文件只记录时间、接口、模型、token 和估算费用，**不会记录聊天正文、Prompt 或 API Key**。

### 计费方式

如果模型响应里有标准 `usage.prompt_tokens` / `completion_tokens`，优先使用真实值。

文本接口没有返回 usage 时，会根据请求与响应文本长度做本地估算，并在仪表盘标记“token 估算”。

**视觉接口例外：** 如果服务商没有返回图片 prompt token，程序会把图片输入 token 标记为“未知”，不会再用 Base64 图片字符串长度去猜计费 token；因此对应费用也可能显示为未知。

明细最多保留最近 5000 条。超过上限的旧明细会合并为按日 / 接口 / 模型汇总（保留约 400 天），所以高频使用也不会因为明细上限而漏掉当月前半段的请求与费用。

统计文件中的 Base URL 只保留 scheme、host、port 和 path；URL userinfo、query、fragment 会在写入前移除，避免把误放在 URL 中的 token 写入统计文件。

费用为本地估算，最终扣费以服务商账单为准。

### DeepSeek V4.1 Flash

2.4 起：

- DeepSeek 官方模型名使用 `deepseek-flash`
- OpenRouter 默认回复模型使用 `deepseek/deepseek-v4.1-flash`
